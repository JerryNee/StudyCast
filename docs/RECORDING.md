# 录制与剪辑

日期：2026-08-12
适用：StudyCast + vendored UxPlay（`third_party/UxPlay`）

这份文件写给接手的开发者或 AI agent。录制这块有几个反直觉的约束，不知道的话
会往死路上走，或者改出一个"看起来正常但静默丢数据"的东西。

## 1. 一切的根源：iOS 镜像整场只有一个关键帧

**实测**（`ffprobe -select_streams v -skip_frame nokey`，统计真实会话录像）：

| 录像时长 | 关键帧总数 |
|---|---|
| 278.7 秒 | **1** |
| 181.1 秒 | **1** |
| 43.1 秒 | **1** |

那唯一的 IDR 在第 0 秒。iOS 在镜像会话建立时发一次，之后**全是 P 帧，永不刷新**
（走 TCP 可靠传输，不需要冗余关键帧）。

这一条推导出下面所有结论，改动录制相关代码前必须先理解它。

## 2. 为什么是"全程录 + 事后裁"，而不是"点了才录"

因为中途开录**没有可解码的起点**。第 5 分钟按下录制时，上一个关键帧在第 0 秒，
从那之后的任何一帧都依赖前面的帧才能解码。

所以现在的架构是：

- UxPlay 从发送端连上就一直录，写成 `master` 文件；
- Record 按钮**只记录时间区间**，不控制录制；
- 停止投屏时用 ffmpeg 从 master 里把标记的区间**重编码**出来。

`runFFmpegTrim` 必须重编码、不能 `-c copy`，原因就是第 1 节：流拷贝需要在切点上
有关键帧，而切点上没有。

## 3. 坑：`-mp4-control` 按需录制目前不可用

vendored UxPlay 里有一个 `-mp4-control <fifo>` 选项（用法见 `uxplay.cpp` 的
`print_info`），建一个命名管道，写入 `start` / `stop` 即可在不断开投屏的情况下
开始/结束录制。**这正是"点了才录"想要的东西，而且实现得相当完整**——有状态
回写、幂等处理、缓存 SPS/PPS 并在开录时注入。

**但它在 iOS 镜像场景下不会工作。** `mux_control_start_recording()` 会把
`mux_video_header_needs_inject` 置真，随后 `video_process()` 里的逻辑是
"等到下一个关键帧再真正开始写"。按第 1 节，那个关键帧**永远不会来**。

实际表现最坑的地方在于它**看起来是成功的**：

```
recording control: start        ← 日志这么打印
```

然后一帧都不会写进文件。没有报错，没有警告。

StudyCast 目前**没有使用**这个选项（Swift 侧搜不到 `-mp4-control`），所以现状
无害。但它在用法说明里公开可见，谁看到都会以为可以直接用。

**要启用它，必须先解决"没有新关键帧"这个问题**，见下一节。

### 它是本地补丁，不是上游功能

上游 UxPlay 没有 `-mp4-control`。它整个来自本仓库的补丁
`third_party/uxplay-patches/0001-Add-mp4-control-start-and-stop-recording-over-a-FIFO.patch`，
所以修不修、怎么修都由本项目决定，不涉及上游。

该补丁的 245 行**全部**服务于 `-mp4-control`：控制状态与 FIFO、Annex-B 解析与
关键帧检测、SPS/PPS 缓存、编解码器信息缓存、以及 `audio_process` /
`video_process` 里的启动门。它原先的标题是 "Fix StudyCast continuous MP4 audio
capture"，与补丁内容毫无关系，已于 2026-08-12 更正——那个标题会让人以为它是个
音频修复，从而既不敢删、也想不到它正是本节这个坑的来源。

**当前它是休眠的**：StudyCast 不传 `-mp4-control`，`mux_control_path` 恒为空，
补丁新增的每个条件都退化回原行为，对运行时净影响约等于零。保留它是因为真要做
按需录制时，控制通道、状态机、生命周期这些都是现成的一半。

## 4. 真要做按需录制，唯一可行的路子

在 StudyCast 侧**解码后重编码**：

- 预览管线本来就在解码（`GStreamerPreviewEngine.mm` 里
  `udpsrc ! rtph264depay ! h264parse ! vtdec ! appsink`）；
- 从解码后的帧另起一条编码分支，Record 时启动、Stop 时收尾；
- 关键帧由我们自己的编码器产生，随时可以开始，第 1 节的限制不复存在。

代价是编码 CPU（三工位并发，VideoToolbox 硬件编码应付得来）。

**画质上不亏**：现在的剪辑本来就是重编码产物，只是把这次编码从"事后"挪到了
"实时"。

## 5. 文件与命名

投屏进行中在 staging（`$TMPDIR/StudyCast/<会话时间戳>/`），停止投屏时搬到
`~/Movies/StudyCast/<Study 名>/<会话时间戳>/`。

| staging | 输出 | 含义 |
|---|---|---|
| `s0.1.H264.AAC.mp4` | `1_Station_1.master.1.H264.AAC.mp4` | 工位 1 的第 1 个片段 |
| `s0.2.…` | `…master.2.…` | 发送端掉线重连产生的第 2 个片段 |
| `s0_r1.1.…` | `…master_r1.1.…` | **接收端重启后**的独立 base |
| — | `1_Station_1.mp4` / `_clip1.mp4` | 剪辑（单段用前者，多段用后者） |

一次投屏可能产生多个片段，来源有两种：**发送端掉线重连**（同一 helper 进程内
自增编号，不会覆盖）和**接收端重启**（新进程，编号从 1 重来，所以必须用独立的
`_r<N>` base，否则会覆盖上一段——这个 bug 修于 `117d04c`）。

每个标记区间按其**起点**匹配所属片段的时间窗口（片段创建时间到最后写入时间），
从该片段裁剪。不能一律用最新片段，否则更早的标记会被静默裁出错误内容。

## 6. 崩溃时会丢多少

UxPlay 的 mp4 管线已改为分片写入（`fragment-duration=2000`
`fragment-mode=first-moov-then-finalise`，见 `third_party/uxplay-patches/0006`，
已提上游 [FDH2/UxPlay#557](https://github.com/FDH2/UxPlay/pull/557)）。

| 情形 | 丢失范围 |
|---|---|
| 发送端掉线重连 | **不丢**（当前片段正常收尾） |
| 接收端崩溃 | **最多丢最后一个分片（≤2 秒）** |
| 正常停止 | 不丢，且收尾成常规 MP4 |

改动前接收端崩溃会丢掉**整场**：默认 mp4mux 要到 EOS 才写 moov，录制期间磁盘上
一直是 0 字节，进程猝死等于什么都没留下，且不可修复（数据从未落盘，`untrunc`
之类工具无从下手）。

真实验证：一次自发的 teardown 崩溃（`pthread_mutex_lock: Invalid argument`）
发生在会话第 43 秒，文件立即可读——1,763,611 字节 / 43.1 秒 / 843 个视频包，
并成功裁出 23 秒剪辑。同一台机器十几分钟前的旧构建，同样的崩溃留下 0 字节。

**空片段的判读**：0 字节的片段其 mtime 从未推进，时间窗口退化成一个瞬间。
`moveMasterToDestination` 会把这类片段的窗口延伸到下一段开始处（末段则到无穷远），
使落在其中的标记能被正确归因并报告为"素材已丢失"，而不是含糊的"找不到片段"。

## 7. 剪辑的编码参数

`runFFmpegTrim` 使用 `-c:v libx264 -preset veryfast -crf 18`。

**`crf` 是画质目标，`preset` 只决定编码器花多大力气达到它。** 同 crf 下用更慢的
preset，画质相同、体积更小。曾经用的是 `ultrafast`，导致剪辑比源片段还大。

实测（10 秒片段，crf 均为 18）：

| 内容 | ultrafast | veryfast |
|---|---|---|
| 文字界面 | 3.17 MB / 0.78s | **1.16 MB / 0.47s** |
| 全动态视频 | 11.37 MB / 0.45s | **2.87 MB / 0.60s** |

体积降 2.7–4 倍，耗时基本持平（文字内容反而更快：ultrafast 吐出的数据量太大，
封装写盘的开销超过省下的编码时间）。

再降 crf 到 20 或 23 还能多省 1.5–2 倍，但那才是真的用画质换体积。**当前刻意
停在 crf 18**——研究素材，免费的那部分已经拿到大头收益。

## 8. 码率参考

| 内容 | 每小时 |
|---|---|
| 静态画面（设置页、锁屏） | 0.02–0.06 GB |
| 一般交互 | 0.14–0.49 GB |
| 全动态视频 | 1.28 GB |

H.264 的 P 帧对静止画面几乎不花钱。三工位一小时的典型会话约 0.6–1.5 GB。

## 9. 音频

镜像音频格式是 **AAC-ELD 44100/2**，剪辑时被解码并重编码为标准 AAC。

**录像没有声音通常不是缺陷**，而是发送端当时确实没有音频输出——AirPlay 镜像只
在 App 实际出声时才发音频包。判断方法是数包和测电平，而不是看容器里有没有音轨
（容器里始终声明 AAC 轨）：

```
ffprobe -v error -select_streams a -show_packets -of csv=p=0 <file> | wc -l
ffmpeg -i <file> -af volumedetect -f null -   # 静音轨会是 -91 dB 或 -inf
```

已验证有声场景：master 5054 个音频包，剪辑 766 个，
mean −35.2 dB / max −14.8 dB。
